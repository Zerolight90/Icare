# 리팩토링 검토

분석일: 2026-09-06. 코드 정적 분석과 프론트엔드 린트 결과다. 아래 변경은 **제안이며 아직 구현하지 않았다**. 보안 항목은 호출 경로에서 확인한 결함으로, 실제 서비스에 공격 요청을 보내 재현하지 않았다.

P0는 배포 전에 우선 차단할 권한 문제, P1은 데이터·기능 정확성, P2는 구조·성능·유지보수 개선이다. 보안·버그 수정과 동작을 유지하는 구조 리팩토링을 별도 변경으로 진행한다.

문서의 `BE`는 `babychatboot_backend/parenting/src/main/java/com/chatbot/parenting`, `FE`는 `babychatboot_frontend/chat-frontend`를 뜻한다. 줄 번호는 분석 시점 기준이며 메서드명도 함께 확인한다.

## RF-01 P0 회원가입 역할과 관리자 권한의 결합

**근거:** `BE/dto/SignupRequestDto.java`의 role은 제한 없는 String이다. `UserController.signup`은 별도 검증 없이 서비스를 호출하고, `UserService.signup`의 68행에서 이를 저장한다. `UserService.login`의 110행은 저장된 role로 토큰을 발급한다. `JwtAuthenticationFilter`는 해당 claim에 `ROLE_`을 붙이고 `SecurityConfig`는 ADMIN을 허용한다.

**영향:** 회원가입에서 관리자 역할 값을 넣고 이메일 인증·로그인을 완료하면, 서버가 서명한 관리자 권한 토큰을 받을 수 있는 경로다. 별도 Admin 레코드를 조회하지 않는 관리 API는 이 토큰으로 접근 가능한 구조다.

**개선:** 일반 가입에서 MOM/DAD만 허용하고 부모 역할과 시스템 권한을 분리한다. 일반 로그인은 서버가 USER 권한을 정하며 관리자 발급 경로는 별도로 둔다. 이미 발급된 잘못된 토큰과 저장된 role 데이터의 정리 정책도 포함한다.

**완료 조건:** ADMIN 및 임의 role 가입은 400, 정상 일반 가입 후 모든 관리자 API는 403, 정상 관리자만 관리 기능에 접근하는 통합 테스트. 토큰 변경 전후 호환성도 검증한다.

## RF-02 P0 육아 일지의 가족 소유권 검사 누락

**근거:** `BE/controller/DailyLogController.java`의 40/54/69/114/160/174/187행 매핑은 principal 존재만 확인한다. `BE/service/DailyLogService.java`의 `getLogs`, `getLogsByRange`, `updateLog`, `deleteLog`에는 요청자 정보가 없고, `addLog`도 User와 Baby를 독립적으로 조회한다.

**영향:** 로그인한 사용자가 다른 가족의 babyId/logId를 지정하면 일지 조회·추가·수정·삭제·CSV 및 건강 문진 경로에서 가족 경계를 넘을 수 있다.

**개선:** 서비스에서 요청자 가족과 아기의 가족을 검증한다. logId 경로는 일지 → 아기 → 가족으로 확인한다. 공통 접근 정책을 아기 CRUD와 재사용하고 관리자 전용 접근은 명시적으로 분리한다.

**완료 조건:** 가족 A/B 사용자와 각각의 아기를 준비해 모든 일지 경로를 검사한다. 같은 가족은 허용, 다른 가족은 정책에 따른 403 또는 404이며 DB 변경·CSV 출력·외부 AI 호출이 없어야 한다.

## RF-03 P0 고정 관리자 자격증명 자동 생성

**근거:** `BE/config/DataInitializer.java:55`의 `initAdminAccount`는 고정 username과 코드에 적힌 비밀번호로 계정을 생성한다. 개발 전용 프로파일 조건은 없다. 판단에 필요하지 않은 비밀번호 값은 여기에 재기재하지 않는다.

**영향:** 해당 계정이 없는 운영 DB에도 예측 가능한 관리자 계정이 생긴다. 계정을 삭제해도 재시작 때 재생성될 수 있다.

**개선:** 운영의 암묵적 자동 생성을 제거하고 명시적 초기화 절차 또는 일회성 보안 설정으로 관리한다. 이미 생성된 계정의 비밀번호 변경·토큰 폐기를 별도로 다룬다.

**완료 조건:** 운영 설정에서 재시작해도 기본 계정이 생성되지 않고, 승인된 초기화 경로로만 관리자를 생성할 수 있다.

## RF-04 P1 채팅 트랜잭션과 실패 응답 불일치

**근거:** `BE/service/GeminiService.java:114`의 `askToGemini`는 트랜잭션 안에서 질문을 저장하고 외부 RAG/LLM을 호출한다. 예외를 잡아 안내 문자열을 반환한다. `ChatController.chat`은 이를 200으로 반환한다. `FE/app/chat/page.tsx`의 `handleSend`는 POST 응답을 사용하지 않고 DB 메시지만 다시 읽는다.

**영향:** 외부 호출 실패가 성공처럼 처리되며 저장되지 않은 안내가 화면에 나타나지 않는다. 외부 API 대기 동안 DB 트랜잭션을 유지한다. DB 예외인 경우에는 내부 rollback-only 상태에 따라 커밋 결과가 달라질 수 있으므로 모든 실패가 질문만 커밋된다고 단정할 수는 없다.

**개선:** 짧은 저장 트랜잭션과 외부 호출을 분리하고 메시지 생성 상태 및 실패를 명시한다. 성공·실패 응답 계약을 정하고 화면에서도 처리한다. 재시도 시 질문 중복 저장을 방지한다.

**완료 조건:** AI 성공/429/timeout/DB 저장 실패를 대역으로 재현해 화면 안내와 저장 상태가 일치해야 한다. 같은 요청 재시도도 중복되지 않아야 한다.

## RF-05 P1 날짜 조회의 끝 경계

**근거:** `BE/service/DailyLogService.java:30`, `:41`은 종료일 다음 날 자정을 end로 계산하고 `DailyLogRepository`의 `...RecordTimeBetween...`을 사용한다. BETWEEN은 양끝을 포함한다.

**영향:** 다음 날 00:00 기록이 전날 조회·CSV·문진 통계에도 포함될 수 있다.

**개선:** `recordTime >= start AND recordTime < end`로 통일한다. 기간 역전과 최대 범위도 검증한다. 건강 문진의 월령은 조회 날짜가 아닌 현재 날짜를 쓰고 있으므로 과거 기록 문진 시 기준일 정책도 함께 확정한다.

**완료 조건:** 시작일 00:00 포함, 마지막 날 마지막 기록 포함, 다음 날 00:00 제외. 하루·기간·CSV·문진 결과가 일치한다.

## RF-06 P1 이미지 검증과 저장 수명

**근거:** `BE/controller/FileUploadController.java`의 `upload`는 문자열 `contains(ext)`로 확장자를 검사한다. 빈 확장자도 이 검사를 통과하며 실제 이미지 내용은 확인하지 않는다. 저장 기본 경로는 `/app/uploads`인데 Compose backend에는 해당 경로의 볼륨이 없다.

**영향:** 허용 목록 밖 입력의 일부가 통과할 수 있고, 컨테이너 교체 시 업로드 이미지가 사라질 수 있다.

**개선:** 확장자를 정확한 집합으로 검사하고 콘텐츠 형식·크기·정상 디코딩을 검증한다. 파일 저장을 별도 서비스로 옮기고 영속 볼륨 또는 객체 저장소를 사용한다.

**완료 조건:** 빈/부분 확장자와 이미지로 위장한 파일은 거부한다. 정상 업로드 이미지는 컨테이너 재생성 후에도 유지된다. 저장·조회 경로 모두 정규화된 기준 디렉터리 안에 머문다.

## RF-07 P1 관리자 비활성화의 효력

**근거:** `AdminService.login`만 active를 검사한다. `setAdminActive`/`deleteAdmin` 이후에도 `JwtAuthenticationFilter`는 서명·만료·role만 확인한다.

**영향:** 비활성화·삭제된 관리자의 기존 JWT가 최대 2시간 권한 검사에 통과할 수 있다.

**개선:** 관리자 요청 시 현재 계정 상태 확인, tokenVersion 또는 폐기 정책을 도입한다. 일반 사용자와 관리자 subject를 구분해 이메일/username 혼용도 없앤다.

**완료 조건:** 관리자 로그인 후 비활성화·삭제·보안상 비밀번호 변경 시 기존 토큰의 처리 결과가 정해진 정책과 일치한다.

## RF-08 P1 비동기 조회 경합

**근거:** `FE/app/chat/page.tsx:54`의 방별 조회와 `handleSend`, `FE/app/dailylog/page.tsx`의 `fetchLogs`에는 요청 취소나 현재 선택 확인이 없다.

**영향:** A방 요청 후 B방으로 이동했는데 A 응답이 늦게 도착하면 B 화면에 A 기록이 표시될 수 있다. 날짜·아기 선택에도 같은 형태의 경합이 있다.

**개선:** 조회 훅에서 AbortController나 요청 식별자를 사용한다. 결과를 적용하기 전에 현재 roomId/babyId/date가 요청 키와 같은지 확인한다.

**완료 조건:** 응답 순서를 역전시키는 화면 테스트에서도 현재 선택의 데이터만 표시된다. 방을 바꾼 뒤 완료된 전송이 다른 방의 메시지를 덮어쓰지 않는다.

## RF-09 P1 입력 검증과 인증코드 처리

**근거:** `SignupRequestDto` 등 요청 DTO에 입력 제약이 없고 가입은 babyNames 크기만 제한한 뒤 babyGenders도 같은 인덱스로 읽는다. `UserController.sendVerificationEmail`은 인증코드를 콘솔에 출력한다. `EmailService`는 `Random`으로 코드를 만들며 애플리케이션 코드에서 발송·검증 횟수 제한을 확인하지 못했다.

**영향:** 누락·불균형 배열에서 예외가 발생하고, 잘못된 입력이 DB 계층까지 전달된다. 인증코드가 로그에 남으며 반복 발송·검증 제어가 부족하다. 외부 프록시에서 별도 제한하는지는 확인하지 않았다.

**개선:** 서버 DTO 검증, 아기별 객체 목록, 타입·길이·수치 범위 제약을 추가한다. 인증코드 로그를 제거하고 보안 난수, 발송 간격, 시도 횟수 정책을 적용한다. 공통 예외 처리로 입력 오류와 권한 오류를 구분한다.

**완료 조건:** null/빈 배열/배열 길이 불일치/음수 분유량/잘못된 날짜가 명확한 4xx가 된다. 코드 만료·시도 초과·재발급이 검증되고 로그에 코드가 없어야 한다.

## RF-10 P2 계층별 책임 분리

**근거:** `AdminService`는 인증·계정·콘텐츠·RAG·통계·일지를 함께 처리한다. `DailyLogController`는 CSV와 AI 프롬프트 생성까지, `BabyController`는 가족 검증과 저장까지 직접 처리한다. `GeminiService`는 방 관리와 모델 호출을 겸한다.

**개선:** 가족 접근 정책 → 아기/문진/CSV 서비스 → 채팅과 AI 어댑터 → 관리자 기능별 서비스 순으로 추출한다. 요청 DTO, 응답 DTO, 공통 오류 응답을 정리한다. 외부 API timeout은 해당 어댑터에서 명시하고 재시도는 중복 부작용까지 고려한다.

**완료 조건:** HTTP 계층에 데이터 접근·프롬프트 조합이 남지 않고, 핵심 업무 테스트를 외부 서비스 없이 실행할 수 있다. 기존 API 계약 변경은 별도로 관리한다.

## RF-11 P2 RAG 적재 경로와 설정 의미

**근거:** 시작 로더는 고정 splitter, 관리자 적재는 DB 설정 splitter를 사용한다. 시작 로더는 검색 결과 하나라도 있으면 전체 리소스 로딩을 생략한다. 관리자 업로드는 UTF-8 변환이므로 PDF/DOCX 파싱 경로가 아니다. `rag_chunk_overlap`은 splitter 두 번째 인수에 전달되지만 시작 로더의 동일 인수 주석은 최소 청크 문자 길이라고 설명한다.

**영향:** 문서 추가·변경이 시작 로딩에 반영되지 않을 수 있고, 관리자가 조절하는 overlap 설명과 실제 동작이 다를 가능성이 있다.

**개선:** 파서·청킹·임베딩 저장을 공통 서비스로 분리한다. 문서 ID/해시/버전/적재 상태로 변경분을 판별한다. 설치된 Spring AI 1.1.5 생성자 시그니처와 실제 청크 결과를 확인해 설정 이름을 교정한다. Tika 리소스의 `*.{docx,doc,...}` 패턴 지원 여부도 실제 파일 fixture로 검증한다.

**완료 조건:** 동일 문서 재적재는 중복되지 않고 변경 문서만 교체된다. TXT/PDF와 지원하려는 Office 파일의 추출 텍스트를 확인한다. 청킹 설정을 바꿀 때 기대한 길이·중복이 관찰된다. dev/prod 벡터 차원 전환은 재임베딩·스키마 계획을 포함한다.

청킹 인수와 리소스 패턴의 라이브러리 동작은 이번에 직접 실행 검증하지 않았으므로 확정 오류로 분류하지 않았다.

## RF-12 P2 조회 확장성

**근거:** `BE/service/AdminService.java:383`은 방 목록을 순회하며 `countByChatRoom_Id`를 호출한다. `getAllUsers`, `searchChatRooms`, 사용자 채팅 기록은 전체 List를 반환한다.

**개선:** 방별 메시지 수를 집계 쿼리/DTO projection으로 가져오고 목록·기록에 페이지 또는 커서를 적용한다. LAZY 연관관계의 추가 쿼리는 SQL 수를 측정한 후 필요한 fetch 전략만 변경한다.

**완료 조건:** 같은 페이지 크기에서 조회 쿼리 수가 방 수에 비례하지 않아야 한다. 다량 메시지에서도 응답 크기가 제한되고 정렬·다음 페이지가 일관되어야 한다. 현재 지연 시간은 측정하지 않았다.

## RF-13 P2 프론트엔드 분리와 린트

**근거:** 일지 621줄, 관리자 챗봇 524줄, 채팅 500줄이며 상태·API·화면이 혼합되어 있다. 린트는 **오류 8개, 경고 11개**로 실패했다. 상세 위치는 [실행·검증 문서](DEVELOPMENT.md)에 있다.

**개선:** 업무별 API·타입·조회 훅을 먼저 분리하고 일지 폼/CSV/문진 패널, 채팅 사이드바/메시지 목록을 추출한다. 페이지 안에서 정의한 `SidebarContent`를 바깥으로 옮긴다. any와 effect 문제는 규칙 비활성화 대신 흐름을 수정한다.

**완료 조건:** 린트 오류 0, 타입 검사 통과, 방 전환·일지 편집·관리자 필터의 동작 유지. 경고도 누락된 의존성의 원인을 확인하고 해소한다.

## RF-14 P2 배포·검증 기반

**근거:** backend Dockerfile은 로컬에서 만든 JAR를 복사한다. Compose는 별도 prod 활성화 없이 dev 기본값을 사용한다. prod는 ddl-auto validate인데 마이그레이션 도구 의존성·스크립트를 확인하지 못했다. 프론트엔드 Dockerfile은 npm install을 사용한다. 테스트 소스는 백엔드 contextLoads 하나이며 프론트엔드 test 스크립트는 없다.

**개선:** 백엔드 컨테이너 빌드에 빌드 단계를 포함하고, 프론트엔드는 잠금 파일 기반 설치를 사용한다. 개발/운영 설정, 스키마 마이그레이션, 업로드 볼륨, 초기화 정책을 명확히 분리한다. 일반 비즈니스 테스트와 DB 통합 테스트, 실제 외부 AI 연결 테스트를 나눈다.

**완료 조건:** 깨끗한 체크아웃에서 문서만 따라 빌드 가능하고 빈 DB에 스키마가 재현된다. 기본 CI는 실제 SMTP·Gemini·운영 DB 없이 실행되며, 최소한 권한·날짜 경계·AI 실패 시나리오를 보호한다.
